## 1. 진행 원칙

1. **한 번에 하나의 단계만** 진행하고, 단계마다 "변경 내용 → 확인 방법 → 사용자 확인" 후 다음 단계로 갑니다.
2. 사용자 확인 없이 정하지 않습니다. 미확정 항목은 추천안을 제시하고 확정을 받습니다.

7. **테스트는 필수일 때만 진행**합니다. 다음 단계가 그 결과에 의존하지 않으면 건너뛰고 7장 "후순위 확인 목록"에 적어 둔 뒤 나중에 한꺼번에 확인합니다. (2026-10-01 사용자 지시)

### S7. 상담 저장 경로 전환 (9개 소단위로 분할)

- **목표**: 상담 화면(1세트 구조)의 저장이 새 테이블로 들어가게 한다. 계약 단위 분리(S10) 전까지의 **임시 방식**이다.
- **저장 방식(임시)**: 상담 1세트를 "인터넷·TV 계약 1건 + 유심 계약 N건(인터넷·TV 계약에 연결)"으로 저장. 삭제 후 재입력 대신 계약·최종상품을 ID로 갱신. `proposal_snapshot` → `contracts.consult_snapshot`.
- **분할 이유**: 상담 저장은 고객·계약·제안·상품·상태·이력·컨택 재안내가 한꺼번에 얽혀 있어, 한 번에 바꾸면 중간에 화면이 깨지고 점검 범위가 너무 커진다.
- **분할 순서의 원칙**: ① 서비스 함수(추가만, 화면 변화 없음)를 먼저 만든다 → ② 불러오기(읽기)를 새 구조로 바꾼다 → ③ 저장(쓰기)을 교체한다 → ④ 상태·이력 → ⑤ 예약·컨택 재안내. 한 번에 소단위 하나만 진행하고, 끝날 때마다 이 문서를 갱신한다.

## 8. DB 구조 (`01_structure.sql` 요약 — 이 장만 읽어도 구조를 알 수 있게 정리)

- 근거 파일: `01_structure.sql`(2026-10-01 수신). 기존 테이블(`customers`, `customer_products`, `customer_contacts`, `customer_status_logs`)의 기존 칼럼·데이터는 바꾸지 않고 **새 칼럼(nullable)과 새 테이블만 추가**합니다. 여러 번 실행해도 안전하고, 오류가 나면 전체가 롤백됩니다(`current transaction is aborted`가 나오면 SQL Editor에서 `rollback;`만 실행).
- 이 장은 코드를 만들 때 필요한 사실 위주입니다. 줄 단위 SQL은 원본 파일을 보세요.

### 8.1 한눈에 보는 구조

```
customers (고객)
 ├ contracts (계약)                    인터넷·TV 계약(home) / 유심 계약(usim, 1회선)
 │   │                                 유심 계약은 linked_contract_id 로 같은 고객의 인터넷·TV 계약에 연결(결합할인 대상)
 │   ├ contract_proposals (제안상품)    계약별 "안내용 번들 스냅샷". 아직 상품 ID가 아님
 │   └ contract_items (최종상품)        상품 ID. 인터넷 / TV / 유심. 상태는 진행(설치) 하나
 └ status_history (이력)               customer_id 필수, contract_id·item_id 는 선택(비면 공통 이력)
뷰: v_contract_overview(계약 + 계산값), v_customer_overview(고객별 유치·지급·환수 집계)
```

- 상태는 **축마다 저장 위치가 다릅니다**: 고객 상태 → `customers`, 계약 상태·지급·환수 → `contracts`, 상품 진행 → `contract_items`.
- **저장하지 않고 뷰에서 계산하는 값**: 유치 여부·유치 건수, 계약취소, 지급이 남은 고객.

### 8.2 `customers` (기존 테이블에 추가된 칼럼)

| 칼럼 | 값 | 설명 |
|---|---|---|
| `customer_status` | 상담대기 / 상담중 / 상담완료 / 이탈 / 제외 | 새 고객 상태(DB 값). 화면 칩에서만 `상담완료`를 `유치`로 표시. 기존 `funnel_status`는 전환이 끝날 때까지 그대로 둠 |
| `status_reason` | 이탈: 기존유지·타사가입·고객부재 / 제외: 오인입·없는번호·테스트·타부서 | 이탈·제외 사유 |
| `consult_substatus` | 고객부재 / 상담예약 / 상품안내 | **상담중일 때만** 쓰는 부가표시 |

- 연락처 중복 방지: **숫자만 뽑은 값 기준 유일 인덱스**(`uq_customers_contact_digits`). 하이픈이 있든 없든 같은 번호는 한 번만 등록됩니다(S1에서 숫자만 저장하도록 바꾼 이유).

### 8.3 `contracts` (계약)

- 키: `contract_id`(자동 번호, 화면 표기 `CT-0001`), `customer_id`(고객 삭제 시 함께 삭제), `seq`(고객 안 순번, `(customer_id, seq)` 유일 — 계약 생성 시 순번이 겹치면 한 번 더 시도).
- `contract_type`: `home`(인터넷·TV) / `usim`(유심 1회선). `linked_contract_id`는 **유심 계약만** 가질 수 있고(DB 제약), 자기 자신은 안 됩니다. 연결 대상이 같은 고객의 `home` 계약인지는 앱(`createContract`)이 확인합니다.
- `label`: 구분 이름(예: A집, 본가).

| 묶음 | 칼럼 |
|---|---|
| 주소 | `address_zip`, `address`, `address_detail` (인터넷·TV = 설치 주소, 유심 = 택배 배송 주소) |
| 계약자·납부 | `contractor_name`, `contractor_relation`, `payment_method` (카드·계좌번호는 저장하지 않고 구분값만) |
| 계약 상태 | `contract_status`(**작성중** / 접수대기 / 접수보류 / 접수불가 / 접수완료, 기본 작성중), `status_reason`(접수불가 사유 등), `received_at`(접수완료 시각), `received_at_source`(log/snapshot/created: 이전 데이터의 추정 출처), `install_scheduled_at`(설치 예정일), `external_ref`(통신사 접수번호) |
| 사은품(계약 단위) | `gift_total`, `gift_card`, `gift_cash`, `gift_extra`, `commission_total`(수수료 합계, 상품별 수수료는 앱이 계산) |
| 지급·환수(계약 단위) | `payout_status`(지급요청/지급보류/지급완료), `payout_at`, `clawback_status`(환수요청/환수보류/환수진행/환수완료), `clawback_amount`, `clawback_reason` |
| 기타 | `consult_snapshot`(jsonb: 이 계약의 추천상품 입력값·제안상품·사은품 수정값), `memo`, `source`, `created_by`, `created_at`, `updated_at` |

- `source`: `legacy`(기존 데이터 이전본, 재생성 가능) / `migrated`(이전 후 확정) / `app`(신규 화면, 기본값).
- **`received_at`은 한 번 기록되면 지울 수 없습니다**(유치 판정 기준). 접수완료 후 상태를 되돌려도 값은 남습니다.

### 8.4 `contract_proposals` (제안상품 — 안내용 스냅샷)

- 키: `proposal_id`, `(contract_id, customer_id)`가 `contracts`를 가리킴(계약 삭제 시 함께 삭제).
- 칼럼: `product_type`(**home** = 인터넷+TV 번들 한 덩어리 / usim), `carrier`, `product_name`, `monthly_fee`, `gift_amount`, `commission`, `detail`(jsonb), `legacy_product_id`, `source`, `created_at`.
- **최종상품 여부(`is_final`) 칼럼이 없습니다.** 상담 저장은 이를 `detail` 안에 담습니다(S7-3 확정): `detail = { consultKey: 상담 화면 상품 ID, isFinal: 최종상품에도 올렸는지, product: 상담 화면 상품 값 }`. 상담 저장이 만든 제안은 모두 **대표(인터넷·TV) 계약**에 붙고, 저장할 때마다 계약 단위로 통째로 교체됩니다(제안 ID 유지 안 함).

### 8.5 `contract_items` (최종상품 = 상품 ID)

- 키: `item_id`(화면 표기 `IT-3938`), `(contract_id, customer_id)`가 `contracts`를 가리킴(계약 삭제 시 함께 삭제).
- 칼럼: `product_type`(**internet / tv / usim**), `carrier`, `product_name`, `monthly_fee`, `commission`, `progress_status`(**설치대기** / 설치완료 / 접수취소), `cancel_reason`, `installed_at`, `detail`(jsonb), `legacy_product_id`, `source`, `created_at`, `updated_at`.
- **추가 TV는 별도 상품이 아니라 TV 상품의 `detail` 안**에 들어갑니다(D3-6). 지급·환수 상태는 상품에 없고 계약에만 있습니다.
- 유심 계약에는 상품을 1회선만 넣을 수 있는데, 이 제한은 DB가 아니라 앱(`addContractItem`)이 지킵니다. 인터넷·TV 계약에는 internet/tv만, 유심 계약에는 usim만 넣을 수 있는 것도 앱 규칙입니다(DB는 세 값만 검사).
- 상담 저장은 한 계약 안에서 **상품 구분(internet/tv/usim)이 같으면 같은 상품**으로 보고 ID를 유지하며 갱신합니다(S7-3). 진행 상태는 건드리지 않습니다.
- **같은 계약·상품을 다시 찾기 위한 키 칼럼이 없습니다.** 상담 저장이 계약·상품 ID를 유지하려면 `detail.consultKey` 같은 값으로 찾아야 합니다(S7-1이 이미 `detail.consultKey`를 넣어 둠).

### 8.6 `status_history` (통합 이력)

- 칼럼: `history_id`, `customer_id`(필수, 고객 삭제 시 함께 삭제), `contract_id`, `item_id`(상품 삭제 시 null로), `event_type`(status_change / memo / contact / contract_deleted …), `target_type`(customer / contract / item), `axis`(status / progress / payout / clawback …), `from_value`, `to_value`, `reason`, `note`, `changed_by`, `changed_at`, `legacy_log_id`, `source`.
- 의미: `contract_id`가 비면 **공통 이력**, 있으면 그 계약의 이력, `item_id`가 있으면 그 상품의 이력.
- 제약: `target_type = 'contract'`이면 `contract_id`가 필수, `'item'`이면 `item_id`가 필수. 그래서 계약·상품을 지울 때 이력을 그대로 두면 이 제약에 걸려 삭제가 실패합니다 → 앱이 삭제 전에 해당 이력을 `target_type = 'customer'`인 공통 이력으로 바꿉니다(S6 `s6DetachHistory`).

### 8.7 트리거(자동 규칙)

- `updated_at` 자동 갱신: `contracts`, `contract_items`.
- `contracts_guard`: ① `received_at`을 null로 되돌리는 수정 차단 ② **계약 삭제는 `작성중`이고 `received_at`이 없을 때만 허용**(예외: `source = 'legacy'` 이전본은 재생성을 위해 삭제 허용). 삭제 차단 시 "접수된 계약은 삭제할 수 없습니다. 상태(접수불가 등)로 처리해 주세요" 오류가 납니다.

### 8.8 뷰(계산값)

- `v_contract_overview` = 계약 전체 칼럼 + `item_count`, `canceled_item_count`, `effective_status`, `is_acquired`.
  - `effective_status`: 하위 상품이 **전부** `접수취소`이면 `계약취소`, 일부만 취소면 계약 상태 그대로(D3 취소율 기준과 동일).
  - `is_acquired` = `received_at`이 있음(접수 이력 있음, 이후 취소돼도 유치로 셈).
- `v_customer_overview`(고객당 1행): `contract_count`, `acquired_contract_count`(유치 계약 수, 취소 포함), `acquired_home_count`, `acquired_usim_count`, `active_contract_count`(그중 취소 아닌 것), `is_acquired`(유치 여부), `first_received_at`(유치 기간 집계 기준), `open_payout_count`(지급요청·지급보류), `unpaid_contract_count`(접수됐고 취소가 아닌데 지급완료가 아님), `open_clawback_count`(환수요청·보류·진행).
- 두 뷰 모두 `security_invoker`라 조회하는 사람의 권한이 그대로 적용됩니다.

### 8.9 권한

- 새 테이블 4개(`contracts`, `contract_proposals`, `contract_items`, `status_history`)와 뷰 2개는 **로그인한 사용자(`authenticated`)만** 읽고 쓸 수 있고 `anon`은 권한이 없습니다(RLS 정책 `... rw for authenticated`). 로그인하지 않으면 모든 저장·조회가 실패하므로 화면에서 안내를 보여야 합니다.

### 8.10 코드를 만들 때 알아 둘 점 (S7 기준)

1. 상담 저장이 쓰는 칼럼 이름은 `saveContractMeta`가 받는 이름과 같습니다(`gift_total`, `gift_card`, `gift_cash`, `gift_extra`, `commission_total`).
2. 계약·상품·제안에는 **"상담 화면 상품 ID" 칼럼이 없어** `detail` JSON 안의 `consultKey`로 다시 찾습니다. 계약 자체에는 키 칼럼이 없어, 대표 계약은 `consult_snapshot`이 있는 가장 최근 인터넷·TV 계약으로, 유심 계약은 스냅샷 최종상품의 키와 같은 `consultKey`를 가진 유심 상품이 든 계약으로 찾습니다(S7-2 확정).
3. 상담 스냅샷은 **계약 단위**(`contracts.consult_snapshot`)이며 **대표(인터넷·TV) 계약이 가집니다**(S7-2 확정). 상담 화면이 1세트 구조인 동안(S10 전까지)의 임시 방식입니다.
4. 접수 이후 계약(`작성중`이 아니거나 `received_at`이 있는 계약)은 삭제할 수 없고, 상담 저장이 상품을 지우거나 바꾸지 않습니다. 상태는 `changeStatus`로만 바꿉니다.
5. 같은 연락처(숫자 기준)는 DB에서 한 번만 등록되므로 중복 등록은 오류가 아니라 "기존 고객 안내"로 처리합니다.
