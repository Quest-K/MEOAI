# 계약 중심 화면 개편 — 0단계 설계서 (복수 계약 규칙)

기준일: 2026-10-07 · 대상: `Supabaseservice.js`(S7 저장 경로), 새 화면 파일, DB 1칼럼
이 단계는 **설계만** 합니다. 코드·DB는 아직 바꾸지 않았습니다.

---

## 1. 목표

| 화면 | 담는 것 |
|---|---|
| 고객상담 (고객상세 흡수) | 기본정보, 가족, 컨택이력, 태그, 특이사항, **계약 카드(계약상품)**, 변경이력 |
| 상품상담 | 추천상품 → 제안상품. 제안상품에서 **[계약등록]** → 계약 신규 생성 |

- **최종상품 단계는 폐지**하고 계약 카드가 그 역할을 합니다.
- 같은 고객이 같은 상품으로 계약을 2건 이상 등록할 수 있어야 합니다 (A집·B집).
- 접수완료 이후에도 계약·상품을 수정할 수 있어야 합니다 (이력을 남기며).

---

## 2. 현재 구조의 한계 (코드 근거)

현재 저장은 **"상담 세트 1개 = 인터넷·TV 대표 계약 1건"** 으로 고정돼 있습니다.

| 위치 | 현재 동작 | 복수 계약에 걸림 |
|---|---|---|
| `s7BuildConsultPlan` | 인터넷·TV 최종상품이 2건 이상이면 **첫 번째만** 계약으로 만들고 경고 | 한 번에 1건만 |
| `s7SaveConsultContracts` | 화면이 기억하는 `carrierContractId` **하나**만 갱신. 없으면 새로 생성 | 계약이 여러 개면 추적 불가 |
| `s7LoadConsultTargets` | `consult_snapshot`이 있는 **가장 최근** home 계약 1건을 대표로 선택 | A집/B집 중 하나만 불러옴 |
| `s7ReplaceProposals` | 제안을 대표 계약 기준으로 **통째로 교체** | 제안이 계약에 묶여 있어 계약 전 제안을 보관할 곳이 없음 |
| `matchKey: 'home'` | 홈 계약 키가 고정 | 같은 키라 2번째 계약이 1번째를 덮어씀 |

→ 상담 저장 방식(통째 저장)을 **"제안은 작업본, 계약은 등록 시점에 1건씩 생성"** 으로 바꿔야 합니다.

---

## 3. 새 모델

```
[고객]  customers
   ├─ consult_draft (신규 jsonb)  ← 상품상담 작업본: 고객정보(휴대폰·기존인터넷·가족) + 제안 목록 + 결합할인
   │
   └─ [계약] contracts  (home 또는 usim, 등록할 때마다 1건씩)
         ├─ contract_items      상품 (인터넷·TV / 유심)
         ├─ contract_proposals  등록 당시 제안 1건 (이 계약의 근거, 읽기용)
         ├─ gift_* / commission_total / address ...
         └─ consult_snapshot = null  (새 계약은 쓰지 않음 → 5번 참고)
```

- **제안(추천 → 제안)** 은 계약이 아니라 **고객의 작업본**입니다. 계약 전이라 계약 ID가 없기 때문입니다.
- **[계약등록]** 은 제안 1건을 계약 1건으로 바꿉니다. 이후 계약은 독립적으로 상태·수정·이력이 관리됩니다.
- 제안이 "등록됨"인지는 **저장하지 않고** 계약 상품의 `detail.consultKey`(= 제안 ID)로 **계산**합니다. 진실의 원천이 하나라 어긋나지 않습니다.

## 4. 규칙

| # | 규칙 |
|---|---|
| R1 | [계약등록]은 제안 **1건 → 계약 1건**. 홈 제안은 home 계약(+ 인터넷·TV 상품), 유심 제안은 usim 계약(+ 유심 상품 1건) |
| R2 | 등록 직후 상태는 **작성중** (`createContract` 기본값). 접수대기 전환은 계약 카드에서 `changeStatus`로 |
| R3 | 같은 제안을 이미 등록했으면 확인창("이미 등록된 상품입니다. 다른 계약으로 하나 더 등록할까요?"). 승인하면 **구분 라벨(예: A집) 입력을 필수**로 함 → A집/B집 |
| R4 | 계약 구분 라벨 + 설치주소는 등록 창에서 입력(주소는 선택, 접수대기 전환 시 입력 권장). 저장 칼럼은 기존 `label`, `address_*` |
| R5 | 사은품·수수료는 **등록 시점의 제안 값**을 계약에 복사(`gift_total/card/cash/extra`, `commission_total`, 상품별 `commission`). 이후 요율이 바뀌어도 계약 값은 그대로 |
| R6 | 유심 등록 시 연결할 홈 계약을 선택(`linked_contract_id`). 같은 통신사 그룹의 홈 계약만 후보. 없으면 미연결로 등록하고 나중에 카드에서 연결 |
| R7 | **접수 전**(작성중·접수대기·접수보류, `received_at` 없음): 계약·상품 자유 수정. 접수 단계(작성중 아님)에서 값이 바뀌면 변경 메모를 이력에 남김 (기존 `s7DiffNote`·`s7WriteChangeMemo` 방식 재사용) |
| R8 | **접수완료 이후**: 수정 가능하되 **사유 필수** + 변경 전/후 메모 이력. 상태는 자동으로 되돌리지 않음 |
| R9 | **지급요청·지급보류·지급완료 이후** 수정 시 추가 경고("지급 상태가 있는 계약입니다"). 사은품·수수료는 자동 재계산하지 않고 "다시 계산할까요?"를 선택하게 함 |
| R10 | 삭제는 기존 규칙 그대로(작성중이고 접수 이력 없을 때만). 접수 이후는 상품 `접수취소` |
| R11 | 첫 [계약등록] 때 고객이 `상담대기`면 `상담중`으로 `changeStatus` (이력 1건). 이미 상담중 이후 상태면 건드리지 않음 |
| R12 | 계약 단위 결합할인: 홈 계약 + 그에 연결된 유심 계약 묶음 기준으로 계산해 계약 카드에 표시(제안 단계는 기존 제안 기준 계산 그대로) |
| R13 | 비로그인이면 [계약등록]은 로그인 안내만 표시 (새 테이블은 로그인 전용 RLS) |

## 5. 구 화면(CS_new.html)과의 충돌 방지

새 화면을 별도 파일로 두므로 id 충돌은 없습니다. 다만 **같은 DB·같은 공용 JS**를 쓰므로 아래를 지켜야 합니다.

**위험:** 새 계약에 `consult_snapshot`을 넣으면, 구 화면의 `s7LoadConsultTargets`가 그 계약을 "대표 계약"으로 잡습니다. 그 상태에서 구 화면이 상담 저장을 하면 새 계약의 상품을 삭제하거나 덮어쓸 수 있습니다 (작성중 계약은 빠진 상품을 삭제하므로).

**해결:** 새 계약은 `consult_snapshot`을 **비워 둡니다**. 등록 근거는 `contract_proposals`(계약 ID 연결 행)에 남깁니다. 구 화면은 스냅샷이 있는 계약만 대표로 찾으므로 새 계약을 건드리지 않습니다.

- 구 화면이 새 계약을 보는 곳은 고객상세의 계약 카드뿐이며, 읽기·상태 변경은 문제없습니다.
- 공용 JS는 **추가만** 합니다. 기존 `s7*` 함수·`saveConsultSet`은 수정하지 않습니다.

## 6. DB 변경 (1건, 추가만)

```sql
alter table customers add column if not exists consult_draft jsonb;
```

- 구 화면은 이 칼럼을 읽지도 쓰지도 않습니다(`buildCustomerPayload`에 없음). RLS 정책은 `customers` 기존 정책이 그대로 적용됩니다.
- 칼럼이 없으면 새 화면은 **브라우저 저장으로 대체**하고 안내 문구를 띄웁니다 (`probeCustomerSchema` 방식과 동일: 있으면 쓰고 없으면 건너뜀).
- `consult_draft` 형태(안): `{ v:1, savedAt, customerInfo:{mobileCarrier, mobileFee, oldInternet, familyLines}, proposals:[...], comboDiscount }`

기존 고객의 처음 열람: `consult_draft`가 없으면 `loadConsultForScreen`(읽기 전용)으로 옛 스냅샷의 고객정보·제안을 **한 번 불러와 초기값**으로 씁니다.

## 7. 새로 추가할 함수 (1단계, `Supabaseservice.js` 끝에 추가)

| 함수 | 역할 |
|---|---|
| `registerContract({customerId, proposal, contractType, label, address, linkedContractId, helpers})` | R1~R6. 기존 순수 함수 `s7HomeContract` / `s7UsimContract` / `s7ProposalRow` 재사용 → `createContract` → `saveContractMeta` → `addContractItem` → `contract_proposals` 1행. **실패하면 방금 만든 작성중 계약을 삭제**해 반쪽 계약이 남지 않게 함 |
| `findRegisteredByProposal(customerId)` | 제안 ID → 등록된 계약 ID 목록. "등록됨" 표시와 R3 중복 확인에 사용 |
| `linkUsimContract(usimContractId, homeContractId)` | 유심 ↔ 홈 연결 변경 (접수 전·후 모두, 이력 메모) |
| `editContractWithReason({contractId, itemEdits, metaEdits, reason})` | R7~R9. 기존 `saveContractItem`·`saveContractMeta` 호출 + 사유·변경 메모 기록. 지급 상태 있으면 경고 정보 반환 |
| `loadConsultDraft(customerId)` / `saveConsultDraft(customerId, draft)` | `consult_draft` 읽기/쓰기 (칼럼 없으면 `{ok:false, noColumn:true}`) |
| `computeContractCombo(homeContractId)` | R12. 홈 계약 + 연결된 유심 계약으로 결합할인 계산용 입력을 만들어 반환 |

모든 함수는 기존과 같이 예외를 던지지 않고 `{ok, ..., error}`를 돌려줍니다.

## 8. 새 화면 구성 (2~3단계 참고)

**고객상담** — 위에서 아래로: 고객 요약줄 → 기본정보 → 가족 → 태그 → **계약 카드 목록**(A집/B집 구분, 접수·지급·환수 칩, 상품 줄, 수정 버튼) → 컨택이력 → 특이사항 → 변경이력(공통/계약별 필터).
**상품상담** — 추천상품 → 제안상품. 제안 카드마다 [계약등록] 버튼과 "등록됨(CT-0001)" 표시. 최종상품 단계와 수수료 패널은 계약 카드(로그인 시)로 이동.

기존 `renderRecoCards`, `renderProposalLists`, 결합할인 아코디언, 계약 카드·이력 렌더 함수는 **그대로 복사해 재사용**하고, 저장·불러오기만 위 함수로 연결합니다.

## 10. 기본값으로 정한 사항 (바꾸고 싶으면 알려 주세요)

1. **작업본 저장 위치**: `customers.consult_draft` 칼럼 1개 추가(6번 SQL, Supabase에서 1회 실행). 칼럼이 없으면 브라우저 저장으로 임시 동작.
2. **유심 연결**: 작성중에서는 선택, **접수대기로 바꿀 때 연결이 없으면 경고만** (막지는 않음).
3. **고객 상태**: 첫 [계약등록] 때 `상담대기`면 `상담중`으로 자동 전환(R11).
